1. Vue d'ensemble du projet
Le projet suit la structure conventionnelle Symfony. Les dossiers standards (Controller/, Entity/,
Repository/) restent plats — un seul niveau, tous les fichiers du même type ensemble. Seul
Service/ est organisé en sous-dossiers par domaine fonctionnel, car sans ça il deviendrait
rapidement illisible avec 30+ services.

  project/
  ├── config/
  │   ├── game/                             # Catalogues YAML (données statiques de game
  design)
  │    ├── packages/                        # Configuration des bundles Symfony
  │    └── services.yaml                    # Déclaration et injection des services
  │
  ├── src/
  │    ├── Controller/                      # Points d'entrée HTTP
  │    ├── Entity/                          # Entités Doctrine (état persisté en BDD)
  │    ├── Integration/                     # Services externes (S3, Discord, Mercure...)
  │    ├── Manager/                         # Liaison entités ↔ repositories (persistance)
  │    ├── Message/                         # DTOs des messages RabbitMQ
  │    ├── MessageHandler/                  # Consumers RabbitMQ (Symfony Messenger)
  │    ├── Repository/                      # Requêtes BDD (Doctrine)
  │    ├── Service/                         # Logique métier, organisée par domaine
  │    ├── ValueObject/                     # Objets immuables sans persistance BDD
  │    └── Validator/
  │       └── DTO/                          # Validation et normalisation des données
  entrantes
  │
  ├── migrations/                           # Migrations Doctrine
  └── tests/
       ├── Service/                         # Tests unitaires
       └── Controller/                      # Tests fonctionnels




1.1 Règles fondamentales
   •   Un Controller ne contient jamais de logique métier. Il valide la requête, appelle un service,
       retourne une réponse HTTP.
   •   Un Service ne retourne jamais une JsonResponse. Il ne connaît pas HTTP.
   •   Un Manager encapsule la persistance : il crée, modifie et sauvegarde les entités via les
       repositories. Il ne contient pas de règles métier.
   •   Une Entity ne charge jamais ses données depuis un catalogue YAML. Elle stocke un slug
       (string) qui fait référence au catalogue.
   •   Un MessageHandler est fin : il orchestre les services, ne contient pas de logique propre.
   •   Les services dans Integration/ ne connaissent pas le jeu. Ils savent uniquement parler à
       un service externe.

3. src/Controller/
Points d'entrée HTTP de l'application. Chaque controller gère un domaine fonctionnel. Structure
interne d'une méthode de controller :

   •   Désérialiser et valider la requête via un DTO (Validator/DTO/)
   •   Appeler le service métier correspondant
   •   Retourner une JsonResponse

  ├── ColonyController.php                  # Gestion des ressources, bâtiments,
  colonisation

  ├── ResearchController.php                # Lancement et suivi des recherches
  ├── CombatController.php                  # Consultation des logs de combat
  ├── PlayerController.php                  # Profil, alliances, contrats
  └── GuildController.php                   # Gestion des guildes et relations inter-guildes


  // Exemple de structure d'une méthode controller
  public function sendFleet(Request $request): JsonResponse
  {
       // 1. Validation
       $dto      = new SendFleetDTO($request->toArray());
       $errors = $this->validator->validate($dto);
       if (count($errors) > 0) {
              $errorResponse = new ErrorResponse($errors);
          return new JsonResponse($errorResponse->getPayload(), $errorResponse-
  >httpStatus);
       }


       // 2. Appel service métier
       $fleet = $this->fleetService->sendFleet($dto, $this->getUser());


       // 3. Réponse
       return new JsonResponse(
          $this->normalizer->normalize($fleet, 'json', ['groups' =>
  ['fleet_show']]),
              Response::HTTP_CREATED
       );
  }

6. src/Manager/
Les managers sont la couche de liaison entre les services métier et les repositories. Ils
encapsulent toutes les opérations de persistance : création, modification et sauvegarde des
entités. Ils ne contiennent pas de règles métier — c'est le rôle des services.

  Manager/
  ├── FleetManager.php                      # Création et mise à jour des flottes et
  FleetShip
  ├── PlanetManager.php                     # Colonisation, mise à jour du statut des
  planètes
  ├── PlayerManager.php                     # Création et gestion des joueurs
  ├── GuildManager.php                      # Création et gestion des guildes et relations
  ├── ColonyManager.php                     # Bâtiments, ressources, défenses sur une
  planète
  ├── ShipyardManager.php                   # File de construction (ShipyardQueue)
  ├── ResearchManager.php                   # File de recherche (ResearchQueue,
  PlayerTechnology)
  └── CombatManager.php                     # CombatEvent, CombatParticipant, CombatLog




6.1 Responsabilité d'un Manager
 Couche                      Fait quoi                            Ne fait PAS
 Service                     Règles métier, calculs, décisions,   Persistance directe, JsonResponse
                             dispatch RabbitMQ
 Manager                     Crée/modifie les entités, appelle    Règles métier, calculs, appels
                             repository.save()                    HTTP
 Repository                  Requêtes BDD (find, filter, count)   Modifier ou sauvegarder des
                                                                  entités

6.3 Les Managers et Integration/
Un Manager peut injecter un service d'Integration/ quand la persistance implique un service
externe. Par exemple, ColonyManager peut injecter S3Service pour stocker une image liée à
une planète — exactement comme DomainManager injectait S3 dans le projet précédent.


      La règle reste la même : Integration/ ne connaît pas le jeu. Le Manager lui fournit les données à
      stocker/supprimer, Integration/ s'occupe du comment.

8. src/Message/ et src/MessageHandler/
Symfony Messenger avec RabbitMQ. Message/ contient les DTOs (objets simples transportés
dans la queue). MessageHandler/ contient les consumers qui traitent ces messages.

                                                                  notifie le joueur via Mercure.
 ResearchFinished.php                      ResearchService        Incrémente PlayerTechnology,
                                                                  notifie le joueur.
 FleetArrived.php                          FleetMovementService   Change le statut de la flotte, crée
                                                                  ou rejoint un CombatEvent si
                                                                  attaque.
 CombatResolve.php                         CombatEventService     Déclenche CombatResolver à
                                                                  T+X, persiste le log, notifie les
                                                                  participants.


  // Exemple de Message — objet simple, pas de logique
  // src/Message/ShipConstructionFinished.php
  class ShipConstructionFinished
  {
       public function __construct(
              public readonly int $shipyardQueueId,
       ) {}
  }


  // Exemple de Handler — orchestre les services, pas de logique propre
  // src/MessageHandler/ShipConstructionFinishedHandler.php
  class ShipConstructionFinishedHandler implements MessageHandlerInterface
  {
       public function __invoke(ShipConstructionFinished $message): void
       {
              $queue = $this->shipyardQueueRepository->find($message->shipyardQueueId);
              $this->shipyardService->completeConstruction($queue);
              $this->fleetNotificationService->notifyConstructionComplete($queue);
       }
  }

10. src/ValueObject/
Objets immuables sans persistance en BDD. Un Value Object représente une valeur métier —
deux instances avec les mêmes données sont équivalentes. Ils n'ont pas d'identifiant, ne
changent pas après construction.

  ValueObject/
  ├── Definition/                           # Objets immuables issus des catalogues YAML
  │   ├── ShipDefinition.php                # Stats d'un type de vaisseau (hp, precision,
  costs...)
  │    ├── BuildingDefinition.php           # Définition d'un type de bâtiment
  │   ├── TechnologyDefinition.php # Définition d'une technologie (effet,
  prérequis)
  │    ├── DefenseDefinition.php            # Définition d'un type de défense
  │   └── RequirementSet.php                # Ensemble de prérequis (techs + buildings +
  ships)
  │
  └── Requirement/                          # Résultats de vérification de prérequis
      ├── RequirementResult.php             # Résultat global (satisfait ou non + liste des
  échecs)
      ├── MissingTechnology.php             # Technologie manquante (slug, niveau requis,

      ├── MissingBuilding.php               # Bâtiment manquant (slug, niveau requis, niveau

9.1 Différence entre ValueObject et Entity
                         Entity                               ValueObject

 Persistance             Oui — table en BDD                   Non — jamais en BDD
 Identité                Oui — ID unique                      Non — défini par ses valeurs
 Mutabilité              Oui — peut changer                   Non — immuable
 Exemple                 Fleet, PlanetBuilding                ShipDefinition, RequirementResult

10.1 Structure d'un DTO
Chaque DTO suit la même structure :
  • Constructeur qui reçoit le payload brut (array) et normalise les valeurs
  • Propriétés publiques typées
  • Méthodes de validation avec #[Constraints\Callback] et messages d'erreur traduits

  // src/Validator/DTO/Shipyard/BuildShipDTO.php
  class BuildShipDTO
  {
       public ?string $shipTypeSlug;
       public ?int        $quantity;


       public function __construct(array $payload)
       {
          $this->shipTypeSlug =
  Normalizer::normalizeString($payload['ship_type_slug'] ?? null);
          $this->quantity      = isset($payload['quantity']) ? (int)
  $payload['quantity'] : null;
       }
